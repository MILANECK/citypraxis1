02 / Public website

Feature inventory

The site helps visitors understand the practice, select a route to care and send a request. It does not book a calendar slot.

01

Responsive navigation

Desktop header, accessible mobile menu, first-appointment call to action, language switch, footer navigation and mobile call/booking shortcuts. The selected language is retained across internal links.

02

Therapy discovery

Homepage therapy cards, therapy and specialization directories, detailed clinical pages, related treatment links, section jump navigation and expandable method/FAQ sections.

03

Team & profiles

Featured practice lead, sortable team roster, individual portraits and profiles. The request link appears only when that person's booking toggle is active.

04

Appointment form

Multi-select concerns, “other concern” text, name, email, phone, urgent request and consent. A profile link can preselect a therapist. Submission creates an inquiry, not a confirmed appointment.

05

Digital receptionist

Consent-first German/English AI chat uses published practice information, answers administrative questions, gathers required details and presents a review before explicit submission. It does not diagnose or see a live calendar.

06

Practical information

Tabbed prices, dated reimbursement data, FAQs, weekly opening hours, Google map with directions, expandable information about the practice and arrival.

07

Editorial media

Hero video or image with poster fallback, crop and overlay controls; therapy and team images; group photograph. Motion effects have reduced-motion fallbacks where implemented.

08

Reviews & social links

Up to three published reviews with optional rating/source; clearly identified placeholder cards when none are published. Instagram/Facebook links appear in the footer when configured.

09

Privacy & access

Cookie information panel and privacy link, form/chat consent, keyboard-oriented controls, visible focus states, semantic headings and mobile layouts.

Motion design

The site uses gradual card reveals, sequential opening-hour and price transitions, fades on the request form and contact map, subtle scroll parallax for the hero video and group photograph, and a timed word reveal in chat. Reduced-motion preferences remove or simplify these effects.

Publishing rule

Only published CMS records appear on the normal public site. Draft editing and the embedded Admin preview are separate from the public content snapshot.

Service boundary

None of these routes reserves a live time slot. The secretary confirms arrangements by phone or email. If AI or email delivery is unavailable, the ordinary form and saved Admin request provide the operational fallback.

Admin modules

Dashboard

Overview

New requests, published content, open drafts, site capacity (if metrics are available) and AI chatbot usage. AI cost comes from OpenAI's reported project costs when its admin connection is configured; conversation counts come from the website's usage markers.

Presentation

Hero image & video

Edit the Home hero's media type, image/poster, video, height, crop, overlay, text and group photo. Draft before publishing.

Reception

Appointment requests

One inbox for chat, standard form and therapist-profile submissions. Status and source filters with counts, CSV export, assignee, notification status/retry, expandable chat provenance and owner-only deletion.

CMS

Pages

Edit structural page copy: H1, second line, eyebrow, introduction, H2/H3 section copy and paragraphs. An embedded, scrollable page preview selects the matching editable field; links inside that preview are inactive.

CMS

Collections

Specializations, Therapies, Team, Reviews, FAQs, Practice fees and Reimbursement each manage repeatable records. Items support drafts, publishing, unpublishing where allowed and revision history; relevant items have order fields.

CMS

Team ordering

Up to 20 profiles. Isabella is pinned as the featured lead; the other people can be reordered by drag or arrow controls, and the saved order drives the public roster. Each profile has a booking-active toggle.

Settings

Practice details

Address, city, phone, email, seven-day hours, payment/urgent text, review section copy, chat emergency text and the bilingual concern buttons used by the booking form.

Assets

Social & media

Publish Instagram/Facebook profile links. Upload/select/download media; PNG/JPEG/WebP images up to 10 MB and MP4 videos up to 60 MB. Referenced media cannot be deleted.

Access

Users, activity & account

Owner creates and enables/disables staff roles; recent administrative actions are listed. Each user can change their password, and the login has a password-recovery flow. Supabase Auth handles credentials when Supabase is configured.

AI usage card, precisely

The cost figure is OpenAI-reported usage for the configured project/model and can lag behind recent activity. It is not the prepaid account balance. OPENAI_MONTHLY_BUDGET_USD is an optional display comparison, not a spending cap; it is hidden when unset. If reporting credentials or usage tracking are unavailable, the card says so rather than inventing a value.

Safety features in the database and chatbot

Database & Admin

Restricted access to patient requests

Supabase tables have row-level security enabled. The browser does not write directly to patient tables; the Node server holds the private database key and checks staff roles. Reception and owners can see requests, while editors manage website content. Admin sessions use HttpOnly cookies, and write operations require origin and CSRF checks. Revisions and an activity log support review of changes.

Chatbot

Limits and a human handoff

Chat requires consent, uses signed 30-minute sessions, has a 30-turn conversation limit and server-side rate limits. It flags emergencies, avoids diagnosis and medical advice, and cannot promise calendar availability. Visitors review their details before sending; only then is the request and transcript saved for reception. The OpenAI request masks recognized email/phone details where possible and asks the provider not to store responses; this does not guarantee anonymity.

Operational limit of these safeguards

Rate limits and the website's AI budget display are not a guaranteed spending cap or a substitute for OpenAI project limits, provider monitoring, backups, retention policy or a security/privacy review.

Local development fallback

When Supabase configuration is absent, the same application uses a local SQLite database for isolated development and tests. Production should be evaluated against its configured Supabase backend, not a local test database.

07 / Operator notes

Deployment & dependencies

The repository is configured for a Node 24 Render service built from main, with a health endpoint at /api/health. The final domain needs to point to a Node-capable host; DNS alone cannot run the backend.

Required for hosted backend

Runtime and database

SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY, SUPABASE_STORAGE_BUCKET, APP_ORIGIN, and a supported Node 24 runtime. Keep the secret key on the server only.

Feature-dependent

AI and email

Chat: CHAT_AI_ENABLED, OPENAI_API_KEY, CHAT_CONVERSATION_MODEL. Cost report: OPENAI_ADMIN_KEY, OPENAI_PROJECT_ID; optional display budget OPENAI_MONTHLY_BUDGET_USD. Email: RESEND_API_KEY, CHAT_NOTIFY_FROM, CHAT_NOTIFY_TO; optional PATIENT_CONFIRMATION_FROM.

Maintenance rules

Content change

Edit and publish in Admin. A Git deployment is not required for ordinary CMS text, team, price or media changes.

Code change

Review and test in the repository, then merge/push to the branch used by the host. Render's current configuration triggers deployment on a commit to main.

Database change

Apply the matching SQL migration to the production Supabase project and verify it before depending on a new dashboard or backend feature.

Backups

Maintain a separate Supabase database/Storage backup and recovery procedure. scripts/backup.mjs is for the local SQLite fallback, not a full hosted Supabase backup.

Security

Use staff roles, strong passwords, HTTPS, private server environment variables and least-privilege access. The app includes origin/CSRF checks and rate limits; monitor logs and account usage separately.

Monitoring

Check the host deployment/health, failed request email notifications, Supabase usage and OpenAI project costs. The website's display budget does not stop spending.

Configuration-dependent items

The code supports AI chat, Resend delivery, Supabase capacity metrics and actual OpenAI cost reporting, but this document does not verify live credentials, applied migrations or current deployment status. Check each service in its own dashboard.

08 / Handover checklist

What the new operator should confirm

These are practical verification steps, not claims that the production environment has already passed them.

  • Confirm the production URL and hosting account owner.
  • Verify the main deployment and /api/health.
  • Confirm Supabase migrations, Auth users, RLS and Storage bucket.
  • Test Owner, Editor and Reception logins and permissions.
  • Review all public German/English copy and legal pages.
  • Check current fees, reimbursement dates, team roster and bookable toggles.
  • Submit a synthetic form, profile and chat request; verify source counts.
  • Confirm reception email delivery and patient-copy sender.
  • Check OpenAI project ownership, cost report and separate provider spending limits.
  • Document production backup, restore and retention procedures.
Patient-data boundary

This website is an appointment-request and content-management system, not an electronic medical record. Do not upload clinical reports into it. Complete the practice's legal, privacy, retention and hosting review before treating it as a fully handed-over production service.
